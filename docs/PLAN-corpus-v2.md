# 测试语料 v2 实施计划（待批准）

目标：把测试从"1 份公文 + 12 个切片"扩展到覆盖 7 类真实文档形态的大规模语料，
用于验证识别器在简历、合同、公文、报告、文献、工资表、通讯录上的召回与误报。

> 状态：**已实施**（2026-10-29）。结果见文末。

## 0.1 已确认决策

| 决策点 | 结论 |
|---|---|
| 模板来源 | 先尝试下载公开空白模板/格式规范，失败则程序化生成 |
| 提取扩展 | 包含（docx 表格/页眉页脚/文本框、pptx 表格、xlsx 合并单元格） |
| 规模 | 7 类 × 12 份 = 84 份 |
| 字段口径 | 每类值池 ≥50，且每类累计注入真值 ≥50 条 |

## 0. 前置事实（已探测）

| 站点 | 可达性 |
|---|---|
| gov.cn / mof.gov.cn / ndrc.gov.cn / stats.gov.cn / openstd.samr.gov.cn | 200 |
| github.com / arxiv.org / chinacourt.org | 超时 |
| samr.gov.cn | 403 |

结论：**无法稳定下载 70 份真实模板**；且真实简历/合同/工资表含真人 PII，授权不明，
不能进入测试语料。因此采用「程序化生成模板 + 少量公开格式规范作参照」的混合方案。

## 1. 合规边界（硬约束）

- 只生成/引用**空白版式**，不下载、不保存真实填写样本
- 不绕过登录、付费墙、验证码；不抓取需授权的文库站点
- 所有生成内容为虚构数据；身份证号校验位有效、手机号用保留测试段
- 下载物（若有）存 `testdata_v2/sources/`，gitignore，记录 URL/许可/时间/sha256
- 产物一律 gitignore，不入库

## 2. 文档类型与规模

每类 12 份，共 **84 份**；每类另出 2 份切片版用于长文档测试。

| 类型 | 主要格式 | 结构要点 | 单份注入 PII |
|---|---|---|---|
| 简历 | docx | 个人信息表、教育、工作、项目、技能证书、自我评价 | 15–25 |
| 合同 | docx | 甲乙方信息、条款（标的/金额/期限/付款/违约/争议）、签署栏 | 20–35 |
| 公文 | docx | 版头、发文字号、签发人、主送、正文、附件、落款、抄送 | 10–20 |
| 报告 | docx + pptx | 封面、目录、章节、数据表、评审专家 | 20–40 |
| 文献 | md + docx | 标题、作者、单位、摘要、关键词、基金、参考文献 | 15–30 |
| 工资表 | xlsx | 表头 + 10–30 行员工（工号/身份证/银行卡/社保/个税） | 30–60 |
| 通讯录 | xlsx + docx 表格 | 姓名/部门/职务/手机/办公电话/邮箱/地址 | 30–60 |

合计注入真值实例约 **1600–2200** 条。

## 4. 必须先补的代码能力（否则测不出）

现有 `documents.py` 只处理：
- docx：**仅段落**（表格、页眉页脚、文本框全部漏掉）
- xlsx：单元格文本
- pptx：文本框（表格漏掉）

简历/合同/通讯录大量内容在表格里，不补这块，测试结果会误导判断。

计划补：

1. `docx`：表格（含嵌套）、页眉页脚、文本框（`w:txbxContent`）
2. `pptx`：表格（`shape.has_table`）、备注页
3. `xlsx`：合并单元格、公式缓存值

单元键扩展为 `para:i` / `table:t/r/c` / `header:1:j` / `footer:1:j` / `slide:i/shape:s/table:r/c`，
写入时按同一键回填。

## 5. 生成器设计

`tools/gen_corpus_v2.py`

```
--types resume,contract,official,report,paper,payroll,contacts
--per-type 12 --seed 42 --out testdata_v2
--formats docx,xlsx,md,pptx      # 默认按类型自然格式
--split-large                     # 长文档额外切分
```

流程：
1. 按类型构造版式（python-docx / openpyxl / python-pptx）
2. 从值池随机组合字段，填充到段落/表格单元格
3. 每个实例记录真值：`{text, type, field, location}`
4. 输出文档 + `manifest.json`（含类型、格式、真值、切分关系）

真值定位到「单元键 + 字符偏移」，与 `documents.read_units` 的切分口径一致，
评估时可直接按单元比对，避免 v1 里"地址被拆成多段"的判定偏差。

## 6. 评估设计

扩展 `tools/eval_corpus.py` → 支持 docx/xlsx/pptx/md/txt，按单元键定位真值。

指标：
- **召回**：按文档类型、实体类型、字段类型三维统计
- **误报**：额外命中，按类型列出
- **白名单**：三类场景（公司简称、本单位名、产品名）各跑一遍
- **格式覆盖**：docx 段落 / docx 表格 / xlsx 单元格 / pptx 文本框
- 输出 `report.json` + 控制台表

验收线（建议）：
- 证件/电话/邮箱/信用代码 ≥ 99%
- 人名 ≥ 95%（含表格内）
- 单位 ≥ 95%，简称单独报告
- 地址 ≥ 90%
- 额外命中需人工确认，不接受"把普通词当 PII"的批量误报

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 网络受限，下载不到模板 | 程序化生成版式；仅用公开格式规范做参照 |
| 模板含真实数据 | 只保留版式，示例值全部替换为虚构值 |
| 表格/文本框提取不全 | P1 先补，未覆盖的位置在报告里显式标注 |
| 规则对表格内短文本失效 | 单元独立识别，短文本的上下文规则需单独校准 |
| 规模大导致评估慢 | 评估按单元并行/缓存分词结果 |
| 生成数据与真实分布偏差 | 保留 v1 语料做对照，报告两者差异 |

## 9. 需要你确认

1. **模板来源**：接受"程序化生成版式 + 公开格式规范参照"，不下载真实填写样本？（推荐）
2. **规模**：7 类 × 12 份 = 84 份、约 2000 条真值，是否够？
3. **是否包含 P1 的提取扩展**（docx 表格/页眉页脚/文本框、pptx 表格）——不做的话表格类文档测不出真实水平
4. **格式范围**：docx/xlsx/pptx/md/txt 是否都要；要不要加 PDF（PDF 只读、不可回写，只能测识别不能测还原）
5. **「字段值不少于 50」的口径**：按"每类值池 ≥50 + 每类累计真值 ≥50"理解是否正确


## 10. 实施结果（2026-10-29）

产出：

- `tools/gen_corpus_v2.py` — 7 类 84 份文档，2409 条真值，seed 42 可复现
- `tools/eval_corpus.py` — 兼容 v1/v2 manifest，按实体类型与文档类型统计
- `presidio_pii/documents.py` — docx 表格/页眉页脚/文本框、pptx 表格/备注、xlsx 单元格

召回（84 份 / 2409 条真值）：

| 类型 | 召回 |
|---|---|
| ID / PHONE / EMAIL / CREDIT / BANK / PERSON / LOCATION / JOB_TITLE | 100% |
| ORGANIZATION | 99.3% |
| 公司/单位简称（hard） | 97.2% |

实施中发现并修复的问题：

1. 身份证校验位为 `X` 时崩溃；加权和误把第 18 位计入
2. docx 表格单元格因 `id(lxml)` 复用被误删（漏掉整格）
3. 座机号（`0551-6xxxxxxx`）未识别
4. `天府大道北段1700号` 这类带方向/路段的地址漏识别
5. `国务院办公厅` 被机构主体尾字规则误杀；`国务院` + `办公厅` 需合并
6. 通用部门名（`研发部/法务部`）被当作机构
7. 职务词表缺常用岗位（架构师/分析师/技术负责人…）
8. `苏浩然` 因"然"被列为非人名字而漏检
9. 生成器把简称写进真值却没写进文档（幽灵真值）

已知限制：

- 无机构后缀的简称（如「中科云谷」）规则无法识别，需别名表或 NER
- 通用部门名不做脱敏（`研发部` 单独出现时）
- 合并单元格会以多个坐标重复抽取（回填无副作用）
